# CareerPilot L12 收尾与封版指南

> 执行结论：方向不变，但范围砍半。将 Reliability / Guardrail 工作全部并入现有 L12，在 1–2 天内完成最小工程闭环，然后停止开发，转入投递和面试准备。

## 1. 为什么值得做，但不能继续扩张

CareerPilot 已经形成完整项目主线：手写 Agent Loop、向量检索、后端实现、离线评测、baseline、Wilcoxon、token / 延迟 / 成本记录和架构取舍。简历底部存在留白，不代表还需要新项目或更多技术名词。

当前真正值得补的是 `loop.py` 的可靠性边界：

- `validate()` 失败后直接抛出异常，没有把校验信息交给模型修复。
- 工具异常虽然会作为字符串回传，但没有独立于 8 轮循环的重试预算。
- 模型生成的工具参数会直接进入工具实现，执行前缺少运行时校验。
- `length` 和轮数耗尽通过异常结束，没有统一、可解释的终止结果。

这不是为了填满简历，而是在现有 Agent Loop 上补齐一个真实缺口。但它的求职价值主要体现为：

1. 一条与真实实现一致的 reliability bullet。
2. 能清楚回答可靠性设计问题。
3. 展示你知道如何让 Agent 在失败时受控结束。

因此，本轮不建立新的开发主线，只完成 L12。

## 2. 时间和范围约束

- 总时间：最多 1–2 天。
- 改动重点：`loop.py`、现有 `schema.py`、必要的测试和 README。
- 不追求生产级错误治理、通用框架或完整可观测性平台。
- 如果某项改动无法直接服务于五个核心目标，放入 `Future Work`，本轮不做。
- L12 和 README 完成后立即封版，不因简历仍有留白继续扩展。

## 3. 校验方案取舍

### 本轮默认选择

保留项目现有的手写 `schema.py::validate()`，在它之上增加失败重试和执行边界控制，不为了增加技术名词临时重写成 Pydantic。

原因：

- 手写 Agent Loop 和校验逻辑是项目当前叙事的一部分。
- 本轮目标是补可靠性闭环，不是替换技术栈。
- 保留现有实现可以降低改动量，更容易在 1–2 天内完成并解释清楚。

### 什么时候才考虑 Pydantic

只有当现有 `validate()` 已经难以维护、多个 schema 出现大量重复代码，或者工具参数模型可以明显复用项目已有 Pydantic 结构时，才考虑迁移。

如果最终使用 Pydantic，需要能解释：它负责的是执行边界的数据校验，并不替代手写 Agent Loop，也不等于引入 LangChain / LangGraph。

## 4. L12 只做五项可靠性改造

### 4.1 输出校验失败后有限重试

现状：`validate()` 失败后直接 `raise ValueError`。

目标：把精简后的校验错误回传给模型，让模型只修复结构或字段，最多重试 1 次。

```text
模型输出
  ↓
validate()
  ├─ 通过 → 返回结果
  └─ 失败 → 回传精简错误 → 重试 1 次
                                  ├─ 通过 → 返回结果
                                  └─ 失败 → 统一终止
```

要求：

- 错误信息只保留字段、原因和预期格式，避免上下文膨胀。
- 重试时要求模型修复格式，不重新扩展任务内容。
- 第二次仍不合法时必须结束，不继续循环。

### 4.2 工具参数执行前校验

`TOOLS` 中提供给模型的 JSON Schema 只是生成提示，不能代替执行端校验。在调用 `TOOL_IMPLS[name](**args)` 前增加运行时校验。

最低要求：

- 工具名存在于允许列表。
- 必填参数存在。
- 参数类型、枚举和必要范围合法。
- 未知参数按统一策略拒绝或过滤。
- 校验失败时工具函数没有被调用。

优先复用 `TOOLS` 中已有定义或 `schema.py` 的手写校验，不建立第二套不一致的 schema。

### 4.3 独立的重试上限

Agent Loop 的最多 8 轮不是重试策略。增加一个独立的错误修复预算。

建议最小配置：

- 输出校验修复：最多 1 次。
- 工具参数修复：最多 1 次。
- 工具执行异常：默认不盲目重试；只有明确判断为临时错误时才允许 1 次。
- 总重试预算：建议 2 次，耗尽后立即终止。

所有重试都必须增加计数；不能通过进入下一轮绕过预算。

### 4.4 统一终止状态

不再让 `length`、轮数耗尽、校验失败和工具异常只以裸异常结束。对外统一返回可判断的运行结果。

建议保持最小状态集合：

- `success`：正常完成并得到合法结果。
- `failed`：校验或工具执行失败，无法产生可靠结果。
- `terminated`：因 `length`、8 轮耗尽、总重试耗尽或重复调用被强制停止。

每个非成功结果附带 `termination_reason`。建议只使用五种最小错误类型：

- `validation_error`
- `tool_argument_error`
- `tool_execution_error`
- `limit_exceeded`
- `duplicate_tool_call`

本轮不设计十余种错误枚举，也不建设复杂错误继承体系。

### 4.5 一个简单的重复调用保护

只检测最明显的无效循环：连续出现相同工具名和相同参数。

建议实现：

```text
current_call = tool_name + JSON.stringify(args, sort_keys=True)
```

- 将当前调用与上一次调用比较。
- 如果完全相同，回传一次“该调用已执行”的提示。
- 再次出现时以 `duplicate_tool_call` 终止。

本轮不做语义等价判断、复杂指纹窗口、并发隔离或跨会话去重。

## 5. 只保留六个核心测试

测试应使用 mock 或固定返回值，不依赖真实模型随机产生错误。

- [ ] **输出校验失败后修复成功：** 第一次输出不合法，回传错误后第二次合法；最终为 `success`，校验重试计数为 1。
- [ ] **输出校验重试耗尽：** 两次输出都不合法；最终为 `failed` 或 `terminated`，不能继续请求。
- [ ] **工具参数错误：** 缺失必填参数或类型错误；返回 `tool_argument_error`，并断言工具实现没有被调用。
- [ ] **工具执行异常：** 工具持续抛出异常；按设定预算结束，不能无限重试。
- [ ] **连续重复调用：** 模型连续返回相同工具名和相同参数；重复保护生效并以 `duplicate_tool_call` 结束。
- [ ] **8 轮耗尽：** 连续产生工具调用直至最大轮数；以 `limit_exceeded` 结束，并确认没有进入第 9 轮。

如实现 `length` 的独立分支，可把它加入 8 轮耗尽测试所在文件，但不要因此扩展出新的测试体系。

每个测试只需要验证三件事：错误被正确识别、重试次数正确、流程能够在上限内结束。

## 6. README 最终实验结论

README 的重点不是证明 Agent 更强，而是如实记录一次基于评测的工程决策。以下数字必须与当前简历保持一致：

- 手工标注 30 条官网 / BOSS 直聘 JD。
- 比较固定 top-5、动态工具检索和全量上下文。
- 逐 JD 评测 gaps recall，配置平凡 / null baseline 与配对 Wilcoxon。
- 知识库约 2.3k token。
- 固定 top-5 成本为 0.0824 元。
- 多轮工具循环成本为 0.4020 元，约为固定 top-5 的 4.88 倍。
- 在当前数据、知识库规模和当时计价口径下，未检出 recall 显著改善。
- L9 报告中 `match_score` MAE 约 20，弱于常数 60 baseline 的 9.3，因此移除该指标。
- 最终在当前任务边界内选择固定 top-5 检索。

### 可直接放入 README 的结论草稿

```markdown
## 实验结论与架构取舍

本项目最初假设：允许模型动态调用检索工具，可能比固定 top-5 检索获得更高的 JD gaps recall。为验证该假设，我手工标注了 30 条官网 / BOSS 直聘 JD，并对固定 top-5、动态工具检索和全量上下文三种方案进行逐 JD 对照评测；同时配置平凡 / null baseline，并使用配对 Wilcoxon 检验比较结果。

在约 2.3k-token 知识库、30 条 JD 与实验时计价口径下，固定 top-5 的成本为 0.0824 元，多轮工具循环为 0.4020 元，后者约为前者的 4.88 倍，但实验未检出 recall 的显著改善。因此，本项目在当前数据规模和任务边界内选择固定 top-5 检索，而未将动态 Agent 检索作为默认路径。

评测也暴露了指标设计问题：L9 报告中的 match_score MAE 约为 20，弱于常数 60 baseline 的 9.3。该分数不能提供可靠的区分能力，因此从最终方案中移除。

这个结果不用于证明 Agent 在所有检索任务中无效；它只说明在本项目当前知识库规模、评测集和成本口径下，动态工具循环没有提供足以抵消复杂度与成本的收益。
```

不要把“未检出显著改善”改写成“证明两种方案完全相同”，也不要为了制造成功结局改变实验结论。

## 8. 面试口述重点

可靠性部分准备回答：

- 为什么给模型看的 JSON Schema 不能代替执行端校验？
- 校验失败后怎样把错误回传给模型，为什么只重试 1 次？
- 为什么重试预算需要独立于 8 轮 Agent Loop？
- 如何定义连续重复调用，为什么本项目不做更复杂的语义去重？
- 达到 `length`、8 轮或重试上限后，调用方会得到什么状态？

但整个项目最强的口述仍然是：

> 我最初假设动态 Agent 检索会优于 fixed top-5，但在 30 条真实 JD 的对照评测中，多轮工具循环成本约为 fixed top-5 的 4.88 倍，却没有检出 recall 显著改善。因此我没有强行采用 Agent，而是在当前任务边界内选择了更简单的固定检索方案。

这个故事体现的是提出假设、设计实验、接受反直觉结果和作出工程取舍的能力，优先级高于继续增加功能。
