# CareerPilot v3 主线提纲

> 这份文档**不给实现代码**。给的是一条需求链：每一级的存在理由，是上一级暴露出的具体问题。
>
> 用法：从 L0 开始，一级一级往下。**不要跳级**——跳过去的那一级正好是面试要问的那一级。
> 每级跑通「验收」再往下。跑不通就停在那里，别往前堆功能。
>
> **每一级的结构固定为：**
> `前置` 开工前必须已有的东西 → `产出` 这一级新建/改动哪些文件 → `做什么` → `会撞上什么` →
> `所以下一级` → `验收` 可勾选的判据 → `卡住了` 排障表
>
> **机制上不让你猜，设计上必须你自己想。** 凡是标 ⬜ 的空格，答案不在文档里，也不要问 AI 要答案
> （见 `vault/00-刨根问底法.md`：AI 可以验证你的答案，不可以代替你产生答案）。
>
> 配套：`CareerPilot-v3-Python函数手册.md`（语法/函数签名速查，不含业务逻辑）。

## 这条链长什么样

```
L0  一次 API 调用           → 模型在编我的经历
L1  简历塞进 prompt          → 输出是散文，没法程序化处理
L2  schema 强制输出          → 知识库塞不进去，且大部分内容与本 JD 无关
L3  检索(前置步骤版)         → 整段 JD 当 query，检索结果全是泛泛之谈  ★转折点
L4  检索变成工具             → 一轮返回 3 个 tool_call，我只处理了 1 个，API 报错
L5  真正的 loop              → 某个工具抛异常，整条流程崩了
L6  错误回传给模型            → 只有一个工具，模型没有"选择"可做
L7  扩到 4 个工具             → 改了 description，不知道是变好还是变坏
L8  标注集                   → 有了 ground truth，但用什么数衡量
L9  指标 + baseline           → 看 usage 发现每轮都在重复为同样的 token 付钱
L10 缓存布局                  → 有了前后对比数字
L11 收口(API/UI/README)
L12 空文件重写 loop.py         ← 唯一不可跳过的一步
```

★ 是整个项目的价值所在。L3 必须**真的写出来并且真的看到它差**，那是简历上「把 RAG 从固定前置步骤重构为模型可调用工具」这句话的唯一凭据。

## L0 — 一次调用，先让链路通

### 前置
- [x] venv 能跑，key 在 `.env` 里
- [x] `client.chat.completions.create` 能返回东西

### 产出
```
main.py          ← 已完成
```

### 做什么
已完成。你现在的 `main.py` 做的就是这件事：读 key → 建 client → 一段硬编码 JD → 打印响应。

**只做两件收尾**：
1. 删掉 `import json` 和 `from http import client`——后者尤其危险，它和你的 `client` 变量同名，
   只是恰好被下面那行覆盖了才没出事。
2. `print(response)` 改成只打印正文（`response.choices[0].message.content`）。
   整个 response 对象刷屏，看不清内容。

### 会撞上什么
- 输出看着挺像样，但它评估的是一个**它想象出来的候选人**。它不知道你是谁。
- 顺带确认了基础设施：key 从哪读、报错长什么样、响应对象的结构。

### 所以下一级
它得知道我是谁。

### 验收
- [ ] 终端打印出一段中文评估，不刷屏
- [ ] `main.py` 在 30 行以内

### 卡住了

|---|---|

### 前置

```

`kb/docs/` 这个路径现在就定下来，L3 会直接在这里扫描。

### 做什么
1. 建 `kb/docs/resume.md`。**用你真实简历的内容**，按 markdown 标题分节
   （`## 教育经历` `## 专业技能` `## 项目经历` …）。
   标题结构在 L3 会变成切块边界，现在写整齐一点后面省事。
2. `main.py` 里读进来（`Path(...).read_text(encoding="utf-8")`，
   **Windows 上 encoding 必须显式写**），拼在 JD 前面。

### 会撞上什么
认真读输出，别扫一眼就过。三件事：
1. 质量确实提升了，因为有事实可依。
2. 它开始**软性编造**：把「有 Python 经验」放大成「具备大规模 Python 工程实践」。
3. 输出是一段散文。你想知道「它给了多少分」，得用眼睛找。想把 30 条 JD 的结果做成表格，做不了。

### 所以下一级
输出必须是机器可读的。这不是为了好看——**没有结构化输出就没有评测，没有评测这个项目的后半段全部不存在**。

### 验收
- [ ] 换 3 份不同的 JD 跑，输出内容确实随 JD 变化（不是套话）
- [ ] 至少发现一处「软性编造」，记进 `vault/00-inbox.md`

|---|---|
| `UnicodeDecodeError` | `read_text()` 漏了 `encoding="utf-8"`，Windows 默认 GBK |
| `FileNotFoundError` | 用 `Path(__file__).parent / "kb" / "docs" / "resume.md"`，不要用相对路径——工作目录取决于从哪运行 |

## L2 — 让输出变成 dict

### 前置
- [ ] L1 验收通过
- [ ] 已实测清楚你的 provider 支持哪种 `response_format`（见上面的分工表）

### 产出
```
agent/
├── __init__.py          空文件
├── schema.py            ANALYSIS_SCHEMA
└── prompts.py           SYSTEM_PROMPT
main.py                  ← 改：用 schema，去掉"请输出JSON"那句话
```

`agent/` 包从这里开始建。**每个目录都要有 `__init__.py`（空文件即可）**，
否则 `from agent.schema import ...` 会 ImportError。

### 做什么

**第一步（故意的错路，只花 20 分钟，两个 provider 都跑）**

在 prompt 里写「请以 JSON 格式输出，字段包括…」，然后 `json.loads` 它。跑 10 次，记下失败次数。

你会看到至少两种失败：
- 输出被 ` ```json ` 包起来 → `json.loads` 直接抛 `JSONDecodeError`
- 字段名飘：这次 `match_score`，下次 `score`；`gaps` 有时字符串数组有时对象数组

**把失败率记进 vault。** 这是第二步的对照组。

**第二步**

改用 API 的结构化输出，把 schema 交给 API 强制。

- Claude：`output_config.format` / json_schema（参数名以你装的 SDK 版本文档为准）
- DeepSeek：**不支持 `json_schema`**（实测 400）。只有 `json_object`，约束弱得多

这个差异不是障碍，是**礼物**：你会在一个不支持的 provider 上踩满所有坑，
再在支持的 provider 上看到它们消失。**双向对照**比单向体验强得多。

**第三步：把 JD 从代码里拿出来**

现在 JD 还硬编码在 `main.py` 里。改成函数参数（`def analyze(jd_text: str)`）。
理由不只是整洁：**L10 做缓存时，JD 必须能被放到断点之后**，现在划清边界，后面不用返工。

### 你必须自己定的（不要抄，这是你项目的语义定义）

⬜ **`match_score` 到底是什么意思？**「进面概率」还是「能否胜任」？**必须选一个并写进 prompt。**
选错不要紧，含糊就完蛋——L8 你要按同一个定义人工标注 30 条，定义模糊会导致你自己前后标不一致。

⬜ **`matched_skills` 里每项要不要带 `evidence` 和 `source`？** 带。理由在 L9（溯源率指标），现在先埋下去。

⬜ **`gaps` 的 severity 分几档？每档的判据是什么？** 写下来，L8 标注时你要用同一套判据。

⬜ **`reasoning` 限制多长？** 不限制会写成小作文。

### 会撞上什么
输出稳定了。你把项目文档、技术笔记也想喂进去，发现两个问题：
- 几万字，token 成本和延迟都难看
- 这个 JD 是后端岗，你那一整章 GIS 笔记跟它毫无关系，**纯粹在稀释注意力**

### 所以下一级
只喂相关的部分。也就是检索。

### 验收
- [ ] `result["match_score"]` 能直接当整数用
- [ ] 连续跑 10 次不抛异常
- [ ] prompt 里**没有**"请输出 JSON"这类话（约束在 API 层，不在 prompt 层）
- [ ] `analyze(jd_text)` 是个能独立调用的函数
- [ ] 第一步的失败率记录已落盘

### 卡住了
| 现象 | 查哪 |
|---|---|
| `ImportError: No module named agent` | 缺 `agent/__init__.py`；或者用 `python -m` 而不是 `python agent/x.py` |
| DeepSeek 报 `response_format type is unavailable` | 它不支持 `json_schema`，只能 `json_object` |
| `json_object` 返回空字符串 | prompt 里必须出现 "json" 字样，这是该模式的硬要求 |
| schema 通过了但字段缺失 | `required` 数组写全了吗；`additionalProperties: False` 加了吗 |

## L3 — 检索，先写成固定前置步骤 ★

> **这一级是全项目最重要的一级，也是最容易被"优化掉"的一级。**
> 你会有一个强烈的冲动：既然最终方案是"检索做成工具"，为什么还要先写一个已知是错的版本？
> 因为「我知道它差」和「我测过它差多少」是两个完全不同的东西。面试官问「这个重构带来了什么收益」，
> 前者答不出数字，后者能。

### 前置
- [ ] L2 验收通过
- [ ] `uv add sentence-transformers numpy`
      （首次 import 会下载模型，约几百 MB，**提前跑一次**别在写代码时干等）

### 产出
```
kb/
├── __init__.py
├── index.py            切块 + 向量化 + 检索
├── index.npz           索引文件（加进 .gitignore）
└── docs/
    ├── resume.md
    ├── project-careerpilot.md
    ├── project-llvm.md
    └── notes-*.md
eval/
└── notes-L3.md         ★ 手工观察记录，这一级的核心产出
agent/
└── retrieval.py        run_workflow(jd) —— 固定前置检索版本，别删
```

### 做什么

1. **补齐 `kb/docs/`。** 简历、每个项目的详细文档、技术笔记。**真东西，别编。**
   建议 5–8 个文件，每个按 `##` 分节。内容不够就先写你真做过的那几件事，宁少勿假——
   L9 的溯源率指标会直接暴露知识库里的水分。

2. **切块。** ⬜ 按 markdown 标题切，不要按固定字数切——**自己想清楚为什么**
   （提示：简历和项目文档本身就有结构；标题本身是有用的上下文）。

3. **embedding + 存盘。** 规模是几百个 chunk。⬜ **不要上向量数据库**——想清楚这个取舍怎么讲。
   索引存成 `.npz`，避免每次启动重新算。

4. **检索。** `整段 JD` → embedding → 和全部 chunk 算余弦 → 取 top-k → 拼进 prompt。
   包装成 `run_workflow(jd)`。

> **这个模块是唯一建议你抄 v2 实现的**（`CareerPilot-v2-代码补充.md` 里有完整代码）。
> 条件：**先在 vault 里把这 4 题的 L2 层答出来，再抄。**
> ① 为什么按标题切块 ② 为什么不用向量数据库 ③ 检索返回 `raw` 还是 `text`，为什么
> ④ 为什么模型要懒加载
> 决策是你的，机械实现不是。省下的一天放到 L8 标注或图论专项上。

### 会撞上什么——这一步必须动手看，不能靠想

拿 **5 份真实 JD**，每份把检索回来的 top-3 **原文打印出来**，逐条人工判断
「这一条跟这个岗位的核心要求相关吗」，记下命中数。写进 `eval/notes-L3.md`。

你大概会看到：
- JD 里 60~70% 篇幅是公司介绍、企业文化、五险一金、"欢迎优秀的你加入"。
  这些内容参与了 embedding，把真正的技术要求信号**平均掉了**。
- 检索回来的往往是知识库里那种"综述性"段落（比如简历开头的自我评价），
  因为它们和"泛泛的一大段话"语义最近。
- JD 里明确写的「熟悉 asyncio 并发模型」这种硬要求，对应的项目文档段落**没被检索到**——
  因为它在整段 JD 的向量里只占几个百分点的权重。

这是定性观察，不是正式指标，但它是下一步的动机来源。

### 所以下一级——这是整个项目的核心推理，你要能一口气说出来

> 检索效果差不是因为 embedding 模型不行，是因为 **query 是错的**。
> 而 query 之所以错，是因为它被写死成了"输入本身"。
> 谁知道该拿什么当 query？只有读完 JD、拆解出「这个岗位实际考察哪几项能力」的那个东西知道。
> 那个东西是模型。
> 所以：检索的**调用时机、query 内容、调用次数**都必须交给模型决定。
> 也就是——把检索从固定前置步骤，变成模型可调用的工具。

**这一级留一个开关**：`run_workflow(jd)` 保留下来，**别删**。L9 有了标注集之后，
你要用同一套指标把它当作 baseline arm 再跑一遍，拿到严格的前后对比数字。

### 验收
- [ ] `python -m kb.index` 能重建索引并打印 chunk 数
- [ ] `python -m kb.index` 底部的自测能打印一次检索结果
- [ ] `eval/notes-L3.md` 里有 5 份 JD × top-3 的人工命中记录
- [ ] `run_workflow(jd)` 能独立调用
- [ ] `index.npz` 已加进 `.gitignore`
- [ ] vault 里那 4 题的 L2 已答（如果你选择抄实现）

### 卡住了
| 现象 | 查哪 |
|---|---|
| 首次 import 卡住不动 | 在下载 embedding 模型（几百 MB），等；或先单独跑一次下载 |
| `python kb/index.py` 报相对导入错误 | 用 `python -m kb.index` |
| 检索分数全都 0.9+ 且区分不开 | 归一化了吗；bge 系列 query 侧要加指令前缀，doc 侧不加 |
| chunk 数只有个位数 | 切块逻辑没生效；`glob` 路径对吗（`**/*.md` 用 `Path.glob`） |
| `json.dumps` 报 float32 not serializable | numpy 标量要 `float()` 转一下 |

## L4 — 第一个工具

### 前置
- [ ] L3 验收通过
- [ ] 已实测你的 provider 一轮能返回几个 tool_call（DeepSeek 实测 3 个 ✅）

### 产出
```
agent/
├── tools.py            TOOLS 定义 + TOOL_IMPLS 映射（先只放 1 个工具）
└── loop.py             ← 最粗糙版本：只处理 1 个 tool_call，只循环 1 次
```

### 做什么

只做 `search_my_experience` 一个工具。**先跑通协议，不要一次上四个。**

要理解的协议（手册 §14 有字段表，但**语义要你自己搞清**）：
- 工具 schema 怎么声明，`description` 写什么
- 响应的 `finish_reason` 会变成 `tool_calls`
- 响应里混着文本和工具调用
- 你要把 **assistant 的整条消息原样追加回 messages**，然后追加工具结果消息
- 工具结果的 `tool_call_id` 必须和请求里的 id 对上

**先写最粗糙的版本**：假设只有一个 tool_call，串行执行，只循环一次，写死。

### 会撞上什么（这是设计好的坑，一定会踩）

模型读完 JD，一轮里直接发起了 **3~5 个 tool_call**（因为它同时想查好几项能力）。
而你只处理了第一个 → 下一轮请求 API 直接报错：有 tool_call 没有对应的结果。

第一反应会是「那我就只让它一次调一个」。**不要这么解决。**
一轮并行 3~5 个检索恰好是你想要的行为——它就是「逐项检索」的物理体现，也是延迟能压下来的原因。

### 所以下一级
循环要能处理 N 个 tool_call，并且要能循环多轮。

### 验收
- [ ] 日志里能看到模型自己生成的 query
- [ ] **停下来读一遍这些 query**——它们应该像「使用 FastAPI 构建异步接口服务」
      而不是「后端开发经验」。看到这个差别，L3 的推理就在你手上闭环了
- [ ] 亲眼看到那个「有 tool_call 没有结果」的报错，把原文记进 vault

### 卡住了
| 现象 | 查哪 |
|---|---|
| 报错说 tool_call 缺少对应结果 | ★ 这是设计好的坑，说明你走对了。往 L5 走 |
| 模型完全不调工具，直接开始编 | `description` 太含糊；或 system prompt 没说清工作顺序 |
| `tool_call_id` 对不上 | 别自己生成 id，用响应里带的那个 |
| 追加 assistant 消息后报格式错 | **整条消息原样放回**，只取文本会丢掉工具调用信息 |
| 工具参数解析失败 | `arguments` 是**JSON 字符串**，要 `json.loads` |

## L5 — 真正的 loop

### 前置
- [ ] L4 验收通过，且**亲眼见过**那个报错

### 产出
```
agent/loop.py           ← 重写：for 循环 + finish_reason 分派 + 并发执行
```

### 做什么
`for _ in range(MAX_ITERS)`，按 `finish_reason` 分派。

### 这一级要自己想清的四个决定

⬜ **① 多个工具结果，放一条 message 还是多条？**
（OpenAI 格式下每个 `tool_call` 对应一条 `role:"tool"` 消息，各带自己的 `tool_call_id`，N 个结果就是 N 条连续消息；
它们靠「紧跟 assistant 之后、下一条 user 之前」的位置隐含成同一批。想清楚为什么这件事重要——
提示：模型会从 message 结构里读到什么信息？它下一轮会怎么调整行为？后果落在哪个指标上？）

⬜ **② 并发执行还是串行？** 检索是 IO/计算混合，线程池够用。注意结果顺序要和请求顺序对应。
（手册 §10 有一个坑：`pool.map` 的异常在**迭代结果时**才抛，这决定了 L6 的 try/except 放哪。）

⬜ **③ `finish_reason` 有哪些分支要显式处理？**
至少：正常结束、要调工具、超长。**其余分支要显式抛错，不要 `else: pass`**——
静默兜底会让你后面看到"模型什么都没做就返回了"这种无法归因的现象。

⬜ **④ 循环上限撞到了怎么办？** 抛错还是降级返回当前结果？两种都有道理，选一个并说得出理由。

### 会撞上什么
某次某个工具抛了异常（网络超时、文件不存在、query 是空字符串），
异常一路冒到 `run_agent` 外面，**整条流程崩了。这次跑的 token 全部白花。**

### 所以下一级
工具失败不能中断流程。

### 验收
- [ ] 一份 JD 端到端跑完
- [ ] 日志里能看到：第几轮、每轮的工具名和 query、本轮几个并行调用
- [ ] 迭代轮数是个合理值（2~5 轮），不是 1 轮也不是撞上限
- [ ] 四个决定都在 vault 里写下了 L2 层理由

### 卡住了
| 现象 | 查哪 |
|---|---|
| 死循环停不下来 | 有分支没显式处理，落到了兜底路径；`MAX_ITERS` 生效了吗 |
| 模型每轮只调一个工具 | ★ 检查决定①，结果的组织方式退化了 |
| 并发后结果串了 | `pool.map` 保序；靠 id 对齐更稳 |
| 第 2 轮就结束，什么都没查 | system prompt 没要求它先拆解能力项再检索 |
| 轮数一直撞上限 | 模型不知道什么时候该收；system prompt 里要给收敛条件 |

## L6 — 错误回传，而不是抛出

### 前置
- [ ] L5 验收通过，且**亲眼见过**工具异常炸掉整条流程

### 产出
```
agent/loop.py           ← 改：execute_tool 包 try/except（约 5 行）
```

### 做什么
工具执行包在 try/except 里，异常转成一个**工具结果**（不是异常），带错误标记，
content 里写清「失败原因 + 建议模型怎么绕」。

`type(e).__name__` + `str(e)` 都要带上——光有消息，模型判断不出是网络问题还是参数问题。

### 这一级是纯设计，代码只有 5 行，但它是这个项目最值得讲的一段

> pipeline 遇错中断，agent 遇错重新规划。
>
> 我把工具异常包装成带错误标记的结果回传，附一句引导语。模型拿到之后会自己换 query 重试、
> 或者换另一个工具、或者放弃这一项继续往下——控制流的恢复策略在模型手里，不在我的 if-else 里。
> 这是 agent 和 workflow 的本质区别，不是"我用了 while 循环"。

### 会撞上什么
现在只有一个工具，模型没什么可"改策略"的——顶多换个 query 重试。
这个机制的价值要等工具变多才显出来。

### 所以下一级
把工具集补齐。

### 验收
- [ ] 手动在检索工具里临时 `raise RuntimeError("测试")`，跑一次
- [ ] 观察模型的反应，**把这段日志存下来**（贴进 `vault/L06-*.md`）——面试可以直接讲这个例子
- [ ] 流程没崩，最终仍然产出了完整结果
- [ ] 记下模型的应对策略是什么（重试？换工具？跳过？）

### 卡住了
| 现象 | 查哪 |
|---|---|
| 异常还是往外冒 | try/except 必须在**工具执行函数内部**，包在 `pool.map` 外面没用（手册 §10） |
| 模型收到错误后卡死重试同一个 query | 引导语要明确建议「换方式或跳过」，不能只说「失败了」 |
| 模型收到错误后直接放弃整个分析 | 引导语里要说清「跳过这一步继续分析」 |

## L7 — 补齐工具集，并开始迭代 description

### 前置
- [ ] L6 验收通过
- [ ] `uv add httpx trafilatura sqlmodel`

### 产出
```
agent/tools.py          ← 扩到 4 个工具
data/
└── company.json        search_company 的本地兜底词表
careerpilot.db          SQLite（加进 .gitignore）
```

### 做什么

**每个工具的存在都要有一个具体需求，说不出需求的工具不要加。**

| 工具 | 它的需求是从哪来的 |
|---|---|
| `fetch_jd` | 真实使用时你手上是一个链接，不是一段文本 |
| `search_company` | 有些 JD 通篇「负责相关系统的设计与开发」，你没法判断这岗位在公司业务里的真实位置 |
| `save_analysis` | 分析结果得留痕，否则跑完就没了，也没法做 UI 的历史列表 |

实现要点（纯工程，照做）：
- `fetch_jd`：`httpx` + `trafilatura` 提正文，**不要自己写 HTML 清洗**
- `search_company`：先用一个本地 JSON 词表兜底，查不到就返回"无公开信息"，**不要阻塞主流程**
- `save_analysis`：SQLModel 落 SQLite

### 这一级真正的工作量不在实现，在 `description`

工具的 `description` 是**代码**，不是注释——它是模型决定"要不要调、什么时候调、参数怎么填"的唯一依据。

⬜ 这四段 description 必须你自己写。**不要抄 v2 那份**——抄了这一级直接归零。

你会经历：
- `search_company` 写得太宽 → 模型每次都调，浪费一轮延迟
- 写得太严 → JD 明显含糊时它也不调
- `search_my_experience` 不写清"不要用整段 JD 当 query" → 模型偷懒直接把 JD 扔进去（**L3 的问题原地复活**）
- `top_k` 不给默认值和上限 → 模型有时填 20

**写 description 的三个着力点**：这个工具做什么 / **什么时候不该调** / 参数长什么样（给正反例）。
第二条最容易漏，也最能减少无效调用。

### 会撞上什么
你改了三版 description，感觉第二版更好，但**你说不出"更好"是多好**。
换一份 JD 试，结论又反过来了。

这时你有两条路：
- 凭感觉定稿（→ 这个项目就退化成了调 prompt，简历上一个数字都没有）
- 建立测量

### 所以下一级
评测集。它是被"我怎么知道这个改动是正向的"逼出来的，不是因为"项目应该有评测"。

### 验收
- [ ] 4 个工具各自能独立调用（`python -m agent.tools` 底部自测跑通）
- [ ] JD 含糊时模型调 `search_company`，JD 详细时不调
- [ ] `search_my_experience` 的 query **全部**是单项能力粒度，没有整段 JD
- [ ] `top_k` 从来没超过上限
- [ ] `fetch_jd` 在一个真实招聘页面上跑通
- [ ] 至少记录了 2 版 description 的对比观察（哪怕只是定性的）

### 卡住了
| 现象 | 查哪 |
|---|---|
| `trafilatura` 提出来是空的 | 很多招聘站是 JS 渲染的，静态抓不到。返回明确错误让模型走 L6 那条路，**不要死磕** |
| 模型把整段 JD 当 query | description 里的禁止说明不够硬；加正反例 |
| `search_company` 每轮都调 | 描述里加"什么时候不该调" |
| SQLite `database is locked` | 并发写；单进程下检查有没有忘记 commit/close |

## L8 — 标注集（最枯燥、最能拉开差距的一级）

### 前置
- [ ] L7 验收通过（**Agent 必须先稳定**，标注期间不要再改 agent）
- [ ] 手上有 30 条真实 JD 的原文

### 产出
```
eval/
├── __init__.py
├── dataset.jsonl        30 行，每行一条 JD + 人工标注
├── annotate.md          ★ 标注准则，先写这个再标
├── aliases.json         技能名归一化词表
└── consistency.md       自我一致性检验记录
```

### 做什么
30 条真实 JD + 人工标注。纯人力，预算 6~8 小时，只能坐下来干。

**每行的字段**（先定死再动手）：
```
jd_id, company, title, jd_text, human_match_score, human_gaps[{skill, severity}], real_outcome, notes
```
`real_outcome` 取值：`未投递 / 已投递-无回复 / 已投递-约面 / 已投递-拒绝`。
它解决**有效性**问题：自我一致性检验验证的是标注"可靠"，不是"正确"。哪怕只有 8 条有真实结果，
也能做小样本方向性验证。面试答法示例：「一致性检验验证可靠性不是有效性；我另外记录了真实投递结果，
30 条里有 X 条有反馈，小样本上标注分与真实结果方向一致，但 X 太小不足以做统计。」

### 标注前必须先定死的三件事（顺序不能反）

⬜ **① `human_match_score` 的分段定义。** 每一档写清判据。用 L2 定的那个语义。
建议分 5 档，每档 20 分。**每档要能一句话说清"什么样的候选人落在这一档"。**

⬜ **② `human_gaps` 的粒度。** 「缺 FastAPI 经验」还是「缺 Web 框架经验」？定一个粒度并贯彻。

⬜ **③ 技能名归一化词表。** 你标注时写「异步编程」，模型输出「asyncio 并发」，
这两个要不要算同一项？需要一张人工维护的 `aliases.json`。

三条都写进 `eval/annotate.md`。**这个文件先写完，再开始标第一条。**

### 三条纪律

1. **先标注，后跑 Agent。** 绝对不能看着 Agent 的输出回头改标注。
   这是最容易发生也最致命的自欺——一旦发生，后面所有数字全部失去意义。
2. **JD 优先用你真的投过的。** 你知道真实结果（有没有回复、有没有约面），这是最硬的 ground truth。
3. **自我一致性检验。** 30 条分两天标（20 + 10），第二天**重标第一天里的 5 条**，算平均差值。
   差值 > 15 分说明标注准则不够清晰，回去修准则再重标。记进 `eval/consistency.md`。

第 3 条是方法论上的加分项。「我先验证了标注本身的可信度」和「我标了 30 条」是两个层级。

### 会撞上什么
标到第 10 条你会发现自己的准则有歧义，想改。
可以改——但**改了要把前面标过的全部重标**，并且把这次改动记进 `annotate.md`。

### 所以下一级
有了 ground truth，用什么数去衡量。

### 验收
- [ ] `eval/annotate.md` 在标注开始前就写完了
- [ ] `eval/dataset.jsonl` 30 行，每行 `json.loads` 都能过
- [ ] `eval/consistency.md` 记了 5 条重标的差值，平均 ≤ 15
- [ ] `aliases.json` 已定稿（**跑 baseline 之前必须定稿**）
- [ ] 标注全程没看过 Agent 输出

### 卡住了
| 现象 | 查哪 |
|---|---|
| 一致性差值 > 15 | 准则太模糊。把每档判据写得更可操作，然后重标 |
| 凑不到 30 条真实 JD | 招聘网站上同类岗位的真实 JD 也算，但要标记「未投递」 |
| jsonl 某行解析失败 | 中文引号、换行符没转义；用 `json.dumps` 生成而不是手写 |

## L9 — 指标与 baseline

### 前置
- [ ] L8 验收通过，`aliases.json` 已定稿
- [ ] `uv add scipy`
- [ ] Agent 代码**冻结**（跑 baseline 期间不改）

### 产出
```
eval/
├── run.py              评测脚本
├── raw_<tag>.jsonl     每次跑的原始结果
└── report.md           ★ 指标报告，追加写不覆盖
```

### 做什么
四组指标。⬜ 每一组你都要能回答「为什么用这个，不用那个」。

**① match_score 相关性 → 用 Spearman 秩相关，不用准确率。**
为什么：打分是连续量，"准确率"需要人为设阈值，阈值一动数字就动，不可信。
你真正关心的是「Agent 的排序和人的排序是否一致」——这个岗位比那个岗位更值得投。
目标：ρ > 0.6 算可用，> 0.75 算好。

**② gaps 的 precision / recall。** 用 `aliases.json` 归一化后做集合运算。
**跑完发现 recall 低就回头加别名，是自欺。** 真要补，两组都得重跑。

**③ evidence 溯源率 —— 全自动的幻觉指标。**
`evidence` 字段是否真的是知识库原文的子串。
这是全项目最漂亮的一个指标：**完全自动、零人工、直接量化幻觉**。

⬜ 要自己定的：归一化尺度（忽略空白？忽略标点？多短的片段不计入？）。
**先定死再跑 baseline**，中途改判定标准会让前后两组数字不可比。

⚠️ 一个实现陷阱：检索返回给模型的内容如果带了标题前缀，模型引用时会把前缀一起引进来，
子串匹配就失败了——**溯源率虚低**。想清楚检索该返回哪个字段。

**④ 成本与延迟。** 平均 in/out token、P50/P95 延迟、单次成本、缓存命中率。

### 叙事预案先行（跑之前写，不许跑完再编）

把预期**不对称地**写下来，跑完只做核对：
- `gaps` 的 recall —— agent 应明显赢（逐项检索本来就是捞回被信号稀释淹掉的能力项）
- `match_score` 的 ρ —— 可能几乎不动（打分主要由模型对 JD 的整体判断决定，检索质量影响的是证据覆盖度）

若结果如预期，简历叙事是：「工具化检索的收益是有边界的——它买的是可溯源性和缺口召回，不是打分准确度。」
若与预期相反，同样如实写。**任何结果都能写出诚实的叙事，但只有跑之前写下的预期才不是自欺。**

### 跑三组，不是一组

| arm | 是什么 | 用来说明 |
|---|---|---|
| `workflow` | L3 留下的那条固定前置检索路径 | 重构的收益 —— **L3 那个开关的兑现时刻** |
| `agent-baseline` | 当前 agent 版本 | 起点 |
| `agent-tuned` | L10 优化后 | 优化的收益 |

（可选第四组：DeepSeek vs Claude 同一套指标，白送一张「质量 vs 成本」权衡表。）

### 一条硬规矩
评测里**不要引入 LLM 做判定**（比如让模型判断两个技能名是不是一回事）。
引入了，指标本身就不可复现——同一份数据跑两次数字不一样，那这个数字就不能写进简历。
**能说清"评测必须是确定性的"，比多两个指标值钱。**

### 会撞上什么
跑 30 条时盯着 usage 输出，你会看到——每一轮迭代，那几千字的简历和知识库摘要都在
**重新作为输入计费**。一次分析 8 轮迭代，同样的内容付了 8 次钱。

### 所以下一级
缓存。注意时序——**是先有测量，才有资格谈优化。** 反过来做的话，你改完了不知道改没改动。

### 验收
- [ ] `python -m eval.run workflow` 和 `python -m eval.run agent-baseline` 都能跑完 30 条
- [ ] `eval/report.md` 里有两组数字，可以直接对比
- [ ] 溯源率的判定规则写进了 `report.md`（保证可复现）
- [ ] 报告里带知识库指纹（哪个版本的 kb 上跑的）
- [ ] Spearman 的 **ρ 和 p 都写出来**，不要只写 ρ
- [ ] 单条失败不会中断整个评测（30 条跑完，失败的记 error）

### 卡住了
| 现象 | 查哪 |
|---|---|
| 溯源率 < 0.3 | 大概率是标题前缀问题，不是模型在幻觉。检查检索返回哪个字段 |
| Spearman 的 p 值很大 | 30 条样本本身偏小，正常。ρ 和 p 都报出来 |
| recall 极低 | 先看 `missed_gaps` 里最常出现的技能名——多半是别名没归一化，不是模型没识别 |
| 跑到第 12 条崩了 | `eval_one` 要包 try/except，单条失败记 error 继续 |
| 成本算不对 | 缓存读/写单价和普通输入不同，分开算 |

## L9.5 — planning 对照实验（半天，回答"要不要 planning"）

### 前置
- [ ] L9 验收通过，三组数字在手
- [ ] `aliases.json` 与知识库均未改动（保证与 L9 可比）

### 产出
```

## L10 — 缓存布局

### 前置
- [ ] L9 验收通过，已有 baseline 数字
- [ ] **切到 Claude**（DeepSeek 只有自动缓存，没有显式断点，这一级做不了）

### 产出
```
agent/loop.py           ← 改：加缓存断点
eval/report.md          ← 追加 agent-tuned 一组
```

### 做什么

**先自己推出布局，别背结论。** 推理起点只有一条事实：
**请求的渲染顺序是 `tools → system → messages`，缓存是前缀匹配——
某个位置改了一个字节，该位置之后的缓存全部失效。**

⬜ 由这一条事实出发，自己排出这张表：

| 内容 | 变化频率 | 该放哪 |
|---|---|---|
| 工具定义 | 永不变 | ? |
| system prompt | 永不变 | ? |
| 简历 + 知识库摘要 | 每用户固定 | ? ← 断点 |
| JD 正文 | 每次不同 | ? |
| 工具调用结果 | 每轮累积 | ? |

排完之后回答：
- ⬜ 断点为什么只需要一个，不需要给 system 单独加？
- ⬜ system prompt 里放 `datetime.now()` 会发生什么？
- ⬜ 为什么工具定义的序列化必须稳定？（dict 顺序、缩进、中文转义都算字节）

**第二轮优化**：上面是静态断点，只缓存到「简历」为止。
循环到第 6 轮时，前 5 轮累积的工具结果每次都在全价重传。
解法是**每轮在最后一个工具结果上放一个滚动断点**。

两个副作用要处理：
- 断点数量有上限。滚动时必须把上一轮的断点摘掉。
- 前缀回溯有窗口限制（大约 20 个 content block）。一轮产生超过这个数量的 block，
  下一轮就找不到上一轮的缓存，**静默 miss**——不报错，只是账单变贵。

### 验证缓存真的生效
看 `cache_read_input_tokens`（第二次请求起应 > 0）和 `cache_creation_input_tokens`（第一次 > 0，之后 0）。
如果 read 一直是 0，说明前缀里混进了变动的东西——**把两次请求的渲染结果 dump 出来 diff**。

### 记录
`cache_read / (cache_read + input_tokens)`，优化前后各一个数。

### 验收
- [ ] 缓存布局表自己填完了，三个问题都答了
- [ ] `cache_read_input_tokens` 第二次请求起 > 0
- [ ] `python -m eval.run agent-tuned` 跑完
- [ ] `eval/report.md` 里三组数字齐了
- [ ] 缓存命中率有明确的前后对比数字

### 卡住了
| 现象 | 查哪 |
|---|---|
| 命中率一直 0 | 前缀里有变动内容。dump 两次请求做 diff，一个字节都不能差 |
| 报错说断点超限 | 滚动时忘了摘掉上一轮的断点 |
| 第 7 轮之后命中率掉下来 | 20-block 窗口限制，一轮产生的 block 太多 |
| 命中了但成本没降 | 缓存写入比普通输入贵。轮数太少时可能确实更亏——**这本身是个值得记的结论** |

## L11.5 — memory 演示（可选，1 天，L11 验收后做）
