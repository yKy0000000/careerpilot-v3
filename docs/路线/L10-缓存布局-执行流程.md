## 一、L10 到底在测什么（先建立心智模型）

L9 的结论是「检索是净负收益」：三臂 gaps recall 无显著差异，但成本差 2.5x（agent 17897 token vs full-context 7136）。

**这个结论有一个隐藏前提：没算缓存。** DeepSeek 有自动前缀缓存，命中的 token 计价约 1/30。开缓存后成本结构变了：

- agent 是多轮循环，第 2 轮起复用第 1 轮前缀 → 命中率高 → 成本可能暴跌
- full-context 单次调用，只能跨请求复用 system+KB 前缀 → 命中率低 → 降幅小

**L10 要回答：开缓存后「2.5x」还剩多少？** 收窄到接近 1x，「检索净负收益」结论要改写。

## 二、已确认的事实（第 0 步产出，不用再验）

1. **缓存字段在**：`usage.prompt_cache_hit_tokens` / `usage.prompt_cache_miss_tokens`，官方直连（`api.deepseek.com`）没被吞。
2. **字段是 extra field**：openai 3.0.0 把它当 extra field——`vars(usage)` 取不到（KeyError），要用 `usage.prompt_cache_hit_tokens` 属性或 `usage.model_dump().get("prompt_cache_hit_tokens", 0)`。
3. **reasoning 无单独计价**：`completion_tokens` 已包含 `reasoning_tokens`，输出项一体计价。
4. **重大发现：`temperature=0` 无效**。deepseek-v4-flash 的 thinking mode 默认开启（effort=high），thinking 模式不支持 `temperature`/`top_p`（传了不报错但不生效）。这解释了 L9 的「11/30 match_score 翻转」「seed=42 无效」——一直在随机采样。**要确定性必须显式 `extra_body={"thinking": {"type": "disabled"}}`。**
5. **带 tools 时 `reasoning_content` 必须逐轮回传**，否则 400。官方推荐 `messages.append(response.choices[0].message)`（SDK 对象会带全 reasoning_content）。
6. **价目（off-peak 人民币，已核官方）**：

| 项 | 单价（元/百万 tokens） |
|---|---|
| 输入·缓存命中 | 0.05 |
| 输入·缓存未命中 | 1.5 |
| 输出 | 4.5 |

命中折扣 = 0.05/1.5 = **1/30**；输出/输入 = 3x。

## 三、三个核心概念（决定你怎么写测量代码）

### 概念 1：前缀缓存命中 = 「从第一个 token 开始的连续相同段」

```
请求1: [SYSTEM 100t][KB 2000t][JD-A 234t]
请求2: [SYSTEM 100t][KB 2000t][JD-B 300t]
        └──────── 命中 2300t ────────┘└ miss 300t ┘
```

中间插一个字节，它后面全部 miss。这是缓存最脆的地方，也是阴性对照的依据。

### 概念 2：命中率 ≠ 省钱，有效成本才是钱

```
命中率   = hit / (hit + miss)                 # 比例，不是钱
有效成本 = miss×1.5 + hit×0.05 + output×4.5   # 元/百万 tokens，这才是钱
```

命中率 70% 但总量翻倍 = 净亏。**只报命中率不带有效成本，就是 L9 砍掉的池化口径的同款错误。**

### 概念 3：命中必须拆「轮内 vs 轮间」

- **轮内命中**（只有 agent 有）：第 N 轮复用第 N-1 轮的完整前缀。架构自带红利，跟 prompt 排布无关。
- **轮间命中**（三臂都有）：跨请求复用 system+KB 前缀。才反映你的排布优化。

不拆会得出「agent 命中率 95%，我的排布真棒」的假结论——其实大部分是轮内自带。

**→ 第 1 步落盘时就要留好这个口子**：agent 每轮单独记 hit/miss（列表），不要只记总和，否则第 7 步拆轮内/轮间要返工。

## 四、有效成本公式（定稿）

```python
# off-peak，人民币，每百万 tokens
有效成本 = miss_tokens × 1.5 + hit_tokens × 0.05 + output_tokens × 4.5
命中率   = hit_tokens / (hit_tokens + miss_tokens)
```

- `output_tokens` = `usage.completion_tokens`（已含 reasoning，不单列）
- `hit_tokens` = `usage.prompt_cache_hit_tokens`（extra field，用属性或 `model_dump()`）

## 八、第 3 步 before 结果（2026-08-24，thinking=disabled 确定性口径）

三臂各连跑两遍取第二遍（`raw_*.jsonl` 已是第二遍正式数据，`report.md` 对应 17:45~18:00 段）。

### 有效成本（30 条总和）

| arm | 命中率 | 有效成本(元) | miss | hit | output | 单条 total_tokens | 平均延迟 |
|---|---|---|---|---|---|---|---|
| workflow | 0.941 | 0.0824 | 1930 | 30592 | 17337 | 1662 | 3.6s |
| full-context | 0.974 | 0.0989 | 1700 | 63616 | 20715 | 2868 | 4.1s |

成本比：agent / full-context = **4.06x**；workflow / full-context = 0.83x。

### 成本结构拆解（L10 最有解释力的一张表）

三臂按 `miss×1.5 + hit×0.05 + output×4.5` 拆输入/输出：

| arm | 输入成本 | 输出成本 | 输入占比 | 总成本 |
|---|---|---|---|---|
| workflow | 0.0044 | 0.0780 | 5.4% | 0.0824 |
| full-context | 0.0057 | 0.0932 | 5.8% | 0.0989 |
| agent-baseline | 0.2211 | 0.1809 | 55.0% | 0.4020 |

**workflow / full-context 账单 94% 是输出，而缓存只优化输入。** 缓存的剩余上限（假设输入 100% 命中）只有 2.5~3.4%——**量化证明了「这个负载下输出才是瓶颈，缓存不是」。**

### 发现 1：reasoning token 是「共同项」，污染了比值

enabled → disabled 的 output 对比：workflow 112094→17337（-84%）、full-context 145736→20715（-86%）、agent 162358→40198（-75%）。

enabled 时 output 里 80%+ 是 reasoning token（按 4.5 元/百万计价）。它是**与架构选型完全无关的巨额共同项**，同时抬高三臂的分子分母，把成本比机械地压向 1。disabled 后共同项移除，成本暴跌 6~12x、延迟降 5~10x。

### 发现 2：归因修正——「证伪」错了，是「混淆项被移除后反转」

| 口径 | agent / full-context 成本比 | 相对上一行变了什么 |
|---|---|---|
| L9 无缓存 · thinking=enabled | 2.5x | — |
| L10 缓存 · thinking=enabled | 1.41x | 只加了缓存 |
| L10 缓存 · thinking=disabled | 4.06x | 又关了 thinking |

**开缓存这一步，成本差确实按预期从 2.5x 收窄到 1.41x——原假设在自己的口径里成立。** 把它掀翻的是「关 thinking」，不是缓存。正确表述：缓存收窄了成本差，但收窄是假性的（reasoning 共同项压比值向 1）；移除共同项后，架构真实成本差暴露为 4.06x。

### 发现 3：命中率是虚荣指标（量化）

agent 单条 JD：输入 14609 token = hit 10031（68.7%）+ miss 4578（31.3%）。
输入成本 = hit 10031×0.05 + miss 4578×1.5 = 501 + 6868 = **hit 占量 68.7%、占钱仅 6.8%**。

命中率 0.687 看似不错，但命中的 token 是七成量、不到 7% 的钱。**缓存命中率 ≠ 省钱率。**

### 发现 4：可迁移规则 N > H/30

每加一轮，成本增量 = `0.05×历史长度(hit) + 1.5×新增长度(miss)`。miss 主导的条件：`1.5N > 0.05H`，即 **N > H/30**。
实测 agent 单条：H/30 = 334，N = 4578，**超出 13.7 倍**。

> 多轮 agent 靠前缀缓存变便宜是错觉：加一轮同时增加 hit 和 miss，miss 单价是 hit 的 30 倍，只要新增内容超过历史长度的 1/30，缓存就救不回来。而「新增」（工具结果 + assistant 调用）随轮数线性增长，是缓存的结构性盲区。这是 L10 唯一普适的机制结论。

### 发现 5：架构结论收口——检索分两半，workflow 净正、agent 净负

配对 Wilcoxon（workflow vs full-context 逐 JD recall，run1/run2 各一次）：

| | run2 | run1 |
|---|---|---|
| workflow 宏平均 recall | 0.646 | 0.655 |
| full-context 宏平均 recall | 0.648 | 0.650 |
| 优/劣/平 | 5/5/20 | 5/5/20 |
| p 值 | 0.6089 | 0.9188 |

**workflow 与 full-context 的 gaps recall 无统计差异**（两次 p 均 ≫ 0.05，20/30 条 recall 完全打平）。此前写的「+0.055」是微平均口径（被 gaps 多的 JD 主导）的采样噪声；宏平均口径只差 0.002~0.005。

| arm | 有效成本 | gaps recall | 定性 |
|---|---|---|---|
| workflow（固定检索） | 0.0824 最低 | 与 full-context 无差异 | 净正：最便宜 + 质量持平 |
| full-context（全灌） | 0.0989 | 基准 | 中性 |
| agent-baseline（工具调用） | 0.4020 最贵 | 无差异 | 净负：贵 4.06x 无质量收益 |

**最终架构结论**：质量三臂打平，成本 workflow < full-context < agent。固定前置检索（单次调用）最优，工具调用（多轮循环）纯负收益。

「平 20 条」的本质：gaps（缺什么）= JD 要求 − 候选人已有的，判断「缺什么」主要靠 JD 文本本身，检索/全灌在「候选人有什么」上信息量等价 → 两种架构 gaps 判断趋同。

「检索净负收益」被拆成两半：L9 错在把 workflow 的 token 记为 `nan`、从未参与成本对比，让「检索」被 agent 单独代表；正确说法是「工具调用检索净负、固定检索净正」。

### 发现 6：L9 基线作废，disabled 为新基线

L9 是 thinking=enabled（随机采样），L10 是 disabled——**两个配置，不能互为基线**。第六、七节的 `0.752/0.721/0.659` 阈值、`±0.04` 波动全部失效。

新基线（disabled 三组）：

|---|---|---|
| workflow | 0.729 | 0.955 |
| full-context | 0.674 | 0.953 |

第 6 步比的是「布局改动前 vs 后」，两边都在 disabled 口径。⚠️ 但 disabled 实测非确定（见发现 8），新基线是「单次采样」带噪声——第 6 步的差异判断不能「任何差异都算真」，必须回到配对检验判显著性。

### 发现 7：两个 L9 悬案被 thinking 统一解释

- ρ 高度不稳（0.06~0.35）+ seed 无效 = thinking 默认开启、temperature 被静默忽略 → 一直在随机采样。
- full-context 延迟最差（38s，比多轮 agent 还慢）= thinking 链长随输入增长，full-context 输入最长 → 思考最久；disabled 后延迟回归正常（4.1s）。

两个独立悬案同一因、解释后异常都消失——诊断正确的强信号。

### 发现 8：确定性验证失败——temperature 始终无效

用 `--tag run1/run2` 连跑两遍 diff `model_result`：**三臂全部 0/30 逐字一致**，每条 JD 有 5~26 处差异（evidence 措辞 → severity 翻档 → gaps 数量变化）。这不是浮点 1e-7 抖动（那只会是稀疏平局翻转），而是**服务端在做真实随机采样**。

结论：`deepseek-v4-flash` 的 `temperature` 参数始终被静默忽略（thinking 开/关都不影响），**无法通过参数拿到确定性**。后果：新基线是带噪声的单次采样；所有质量/成本结论必须走「多次跑 + 配对检验」；附带发现 agent 轮数 disabled 后均值 2.43~2.67（略低于 L9 enabled 2.7），「关 thinking 用多调工具补偿」假设不成立。

### ⚠️ 项目级检查项：共同项污染比值

本项目第二次撞同一个病灶：

| 层级 | 病灶 | 后果 |
|---|---|---|
| L9 | gaps 池化：30 条 JD 并成大集合 | 分母虚大 → recall 虚高 0.94（真值 0.66~0.75） |

## 九、第 7 步拆轮内/轮间结果（零成本，读 per_turn_cache）

| 4 | 29568 | 6570 | 0.818 | 4 |

### 表 2：轮内 vs 轮间拆分

| 类型 | token | 占命中 | 占输入 |
|---|---|---|---|
| 轮间命中（turn1，跨请求复用 system+tools） | 33408 | 15.8% | 10.0% |
| 轮内命中（turn2+，复用前一轮前缀） | 178176 | 84.2% | 53.3% |
| 新增 miss（每轮新塞的工具结果+assistant） | 123000 | — | 36.8% |

### 三个结论

1. **agent 命中 84% 是「轮内」**——复用自己前一轮的前缀，架构自带红利，不是排布挣的。执行流程第三节「不拆会误以为排布真棒」的警告被实测坐实。
2. **hit 占量 63%、占钱仅 5.4%**——命中率是虚荣指标的直接实证（`hit×0.05 / (hit×0.05 + miss×1.5)`）。
3. **成本大头是「新增 miss」，且集中在 turn2**：turn2 的 miss 88050 占全部 miss 的 71.6%——第一轮工具调用塞进来的检索结果（8.8 万 token）是缓存结构性盲区的主体。

这就是「缓存只省重复不省新增」的实测证据：发现 4 的 `N > H/30` 不再是推导，是这张表。
